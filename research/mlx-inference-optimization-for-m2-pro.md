# MLX inference optimization research for this M2 Pro

**Scope.** This report targets the existing project configuration: Apple M2 Pro MacBook Pro, 16 GB unified memory, `mlx-community/Llama-3.2-1B-Instruct-4bit`, MLX LM, and one interactive request at a time. The goal is faster local chat, measured against the existing five-task × four-input-length benchmark. This is a research shortlist, not a claim that any proposed change will improve this model. Unless explicitly called a source-backed mechanism below, expected performance outcomes are hypotheses to test on this Mac.

## What matters in the current workload

The saved diverse baseline records MLX 0.32.2, MLX LM 0.31.3, macOS 15.6.1, 16 GiB RAM, 62–4,096-token prompts, and roughly 0.8–1.6 GB MLX peak memory. Its pooled decode speed trends down from about 224 tokens/s at 64 input tokens to about 136 tokens/s at 4,096; TTFT trends up from about 0.12 s to about 2.2 s. The benchmark runs greedy generation, a 128-token output cap, concurrency one, a new KV cache for every request, and no prompt cache. Thus decode/token latency and long-prompt prefill/TTFT are the practical targets; multi-request throughput and avoiding out-of-memory at much larger model sizes are not current bottlenecks.

Apple describes unified memory as an advantage for ML workloads on Apple silicon; MLX is designed for Apple silicon and exposes unified-memory arrays and Metal GPU execution. [Apple WWDC24: Train your machine learning and AI models on Apple GPUs](https://developer.apple.com/videos/play/wwdc2024/10160/), [MLX repository](https://github.com/ml-explore/mlx).

## Transferable techniques, ranked for this Mac

| Priority / technique | Source-backed mechanism | Expected effect (hypothesis for this setup) | Fit, complexity, and risks | How to test with this suite |
|---|---|---|---|---|
| **1. Tune prompt-prefill chunk size** | MLX LM exposes `--prefill-step-size`; its implementation processes the prompt in chunks and documents that smaller values lower peak prefill memory. Current default is 2,048 tokens. [MLX LM `generate.py`](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/generate.py) | Could change prefill throughput, TTFT, and temporary peak memory, especially at 2K/4K prompts. No expected decode-speed change. Direction is hardware/model/shape-dependent. | Excellent fit; low-to-medium complexity. Larger chunks may raise temporary memory; smaller chunks add launches/overhead. | Change only the chunk size (e.g. 256, 512, 1,024, 2,048, 4,096), hold everything else fixed, then compare same-length per-prompt TTFT, prefill tok/s, and peak memory. The current result metadata says 2,048 and matches the installed MLX LM 0.31.3 default, but the runner does not pass the parameter explicitly; expose it before sweeping and record the selected value. Re-run a finalist to check variance. |
| **2. Optimize the actual repeated-chat prefix path** | MLX LM supports saving/reusing prompt KV state; its current generation and server code also contain prompt-cache/reuse paths. This skips recomputation for already-processed prefix tokens. [MLX LM README](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/README.md), [generation code](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/generate.py) | Can reduce TTFT/prefill work when a stable system prompt or prior conversation prefix is reused; should not make a fresh unrelated prompt or token-by-token decode materially faster. | High fit for actual chat sessions with history, but not represented by the current fresh-cache benchmark. Medium complexity: cache lifecycle, prefix matching, invalidation, memory growth, and correct chat-template/token-prefix handling. | Add a separate continuation workload: same system prompt and conversation prefix, then successive turns with growing history. Compare full recompute against cache reuse with identical turns/outputs and measure TTFT and memory. Do not mix those results into the current no-cache baseline. |
| **3. Test `mx.compile`/compiled generation only after profiling** | MLX supports tracing/compiling array computations; compile can reduce Python/runtime overhead for repeatable graphs, but dynamic shapes/state and compilation warmup matter. [MLX compile guide](https://github.com/ml-explore/mlx/blob/main/docs/src/usage/compile.rst) | Potentially lower per-token Python dispatch overhead / decode latency; could help little if model kernels dominate. First request may be slower from trace/compile setup. | Medium fit, medium/high complexity. MLX LM may already use compilation selectively; inspect the exact pinned version before duplicating it. Shape-specialized traces may cause repeated compile overhead or memory use with variable prompt lengths. | Compare eager/current behavior against an explicit, supported compile path in the same process and separately report compile/warmup vs steady-state. Use all four lengths, same prompts, and the same number of warm/measured requests. A speedup only after excluding user-visible first-run cost is not an unconditional interactive win. |
| **4. Benchmark alternative weight quantization / kernel formats** | MLX supports quantized linear layers and fused quantized matrix-vector/matrix-matrix operations. [MLX quantized layers](https://github.com/ml-explore/mlx/blob/main/mlx/nn/layers/quantized.py), [MLX `quantized_matmul`](https://github.com/ml-explore/mlx/blob/main/mlx/core/metal.py) | Smaller/appropriate quantized weights may reduce memory traffic and improve decode, but kernel choice, group size, and quality trade-offs can dominate; an even lower bit count is not guaranteed faster. Prefill may benefit differently from one-token decode. | Good research fit because decode is central and model is already 4-bit. Medium/high complexity: use a compatible converted model variant, track exact weight config, and check quality. Never overwrite the reference weights. | Treat every quantized artifact/config as a distinct model experiment. Run exact same prompt suite and decode controls; report TTFT, prefill/decode tok/s, memory, and a small fixed output-quality check. Include model/config identifier and weight hashes. Do not compare speed alone if output quality changes. |
| **5. KV-cache quantization, only if context/memory pressure justifies it** | MLX LM supports `--kv-bits`, group size, and a delayed quantization start. Current implementation is optional; the MLX Swift documentation explains the basic trade: lower long-context cache memory via compression. [MLX LM generation args](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/generate.py), [MLX Swift KV-cache quantization guide](https://github.com/ml-explore/mlx-swift-lm/blob/main/Libraries/MLXLMCommon/Documentation.docc/kv-cache-quantization.md) | Likely lowers KV memory at sufficiently long contexts; it should not reduce prompt prefill, and may add quantize/dequantize work to decode. At only 4K context on a 1B 4-bit model with ample observed headroom, speed benefit is unlikely. | Low priority for current 16 GB / 4K workload; medium risk due to quality and implementation/model-cache compatibility. | First record a memory/quality need. If tested, compare unquantized KV to selected bit widths at identical lengths, measure decode tok/s and peak memory, and validate deterministic outputs or quality. Treat memory-only gains as such; do not claim speedup without evidence. |
| **6. Speculative decoding with a draft model** | The original speculative-decoding algorithm drafts multiple tokens with a smaller model and verifies them in parallel with the target while preserving the target distribution. MLX LM exposes a `--draft-model` and draft-token count. [Leviathan et al., 2023](https://arxiv.org/abs/2211.17192), [MLX LM `generate.py`](https://github.com/ml-explore/mlx-lm/blob/main/mlx_lm/generate.py) | May raise decode tok/s if draft cost is outweighed by target verification and enough tokens are accepted. For a fast 1B model, the extra model's compute/memory and draft acceptance may erase gains; it will not fix prompt prefill and can worsen TTFT/startup. | Technically supported but low/uncertain fit. Medium/high complexity: another model, memory footprint, cache coordination, output-equivalence validation. | Only after baseline and simpler knobs. Use identical prompts and generation budget, track output/token equivalence, TTFT, decode tok/s, and combined peak memory; separately report draft load/startup. Include short outputs, since interactive answers can end before speculation amortizes. |
| **7. Profile before writing custom Metal kernels** | MLX is built for Apple silicon and includes Metal-backed operations, including quantized matmul and scaled dot-product attention. Apple documents the unified-memory/Metal execution model. [MLX repository](https://github.com/ml-explore/mlx), [Apple WWDC24 GPU session](https://developer.apple.com/videos/play/wwdc2024/10160/) | A custom fused kernel can help only if profiling identifies a costly operation not already handled well by MLX. Given the small model and existing optimized kernels, a custom kernel is an open-ended possibility, not a forecasted win. | Potentially high payoff but high complexity and correctness/maintenance risk. Do not start here. | Use MLX/Metal profiling first, identify a dominant op and shape, then make a minimal isolated prototype. Compare full end-to-end suite plus microbench, correctness, and memory. A microbenchmark win alone is insufficient. |

## Major-serving techniques with low relevance here

Continuous batching and PagedAttention are important at high concurrency: the PagedAttention paper motivates them around serving many requests, KV-memory fragmentation/duplication, and maximizing batch throughput. Our workload is one user and concurrency one, so neither is a near-term optimization target. [Kwon et al., PagedAttention/vLLM](https://arxiv.org/abs/2309.06180). Tensor/pipeline parallelism, multi-GPU scheduling, disaggregated prefill/decode, and fleet-level admission/caching likewise optimize large distributed serving, not this one-model, one-Mac path. They may matter if the project generalizes later, but should not displace local measurements now.

## Suggested experiment order

1. Keep the saved diverse baseline untouched as the reference; record Git revision, package versions, model ID/hash, machine/power conditions, and every changed parameter for each trial.
2. First test prefill chunk size, since it is a direct exposed MLX LM knob and current long-prompt TTFT grows with input length.
3. Separately model actual multi-turn interaction and test prompt/KV-prefix reuse; avoid claiming a benefit from the current no-cache request suite.
4. Profile; test compilation only if the installed MLX LM path leaves a plausible Python/graph overhead opportunity.
5. Then explore quantized weight variants and, only if there is memory pressure, KV quantization. Speculative decoding follows only if long enough outputs make draft verification plausible.
6. Keep one variable changed at a time. Use repeated runs and per-prompt as well as pooled medians/p95; compare outputs/quality and memory alongside speed. Run primary latency tests without telemetry, with any `powermetrics` capture as a separate diagnostic run.
